# Post-Purchase Auto-Email: Implementation Plan

Responds to [020--llm--post-purchase-auto-email-spec](./020--llm--post-purchase-auto-email-spec.md).
Discussions resolved in chat; decisions summarised below.

---

## Decisions

| Question | Decision |
| --- | --- |
| Trigger paths | Both: `/api/intake` (website) AND `/api/stripe/pos` (Terminal) |
| Email history storage | Both: lightweight `email_status` field on Jobs + dedicated `EmailEvents` collection |
| Event dispatcher | Build now, design for future e-blast/segmentation expansion |
| Templates | Plain HTML/text via Resend SDK (React Email deferred). NOT a purchase confirmation (Stripe handles receipts) — this is a **repeat-purchase coupon** sent 10 days post-purchase. |

## Architecture Overview

```
                      TRANSACTIONAL (automatic)              BROADCAST (manual, future)
                      ========================              ===========================

Stripe/webhook ──┐                                               Admin UI
                 ├─► Event Dispatcher ◄── cron / scheduled       Campaign Builder
Intake form ─────┘       │                                        │
                          ▼                                        ▼
                    Email Engine                             Segment Resolver
                    (render + send)                          (query clients by
                          │                                   tags, consent, source,
                          ▼                                   job_type, purchase history)
                      Resend API                                    │
                          │                                         ▼
                    EmailEvents                                  Resend API
                    (audit log)                              (batch send w/ rate limit)
                                                                   │
                                                             EmailEvents
                                                             (per-recipient audit)
```

**Key design principle**: Transactional emails (triggered by code events) and broadcast emails
(triggered manually by admin against a segment) share the same Resend provider, the same
template system, and the same EmailEvents audit trail. The only difference is HOW the
recipient list is assembled: a single recipient from a code event, or a batch resolved
from a Client segment query.

### Events (Phase 1 — transactional only)

| Event Name | Trigger Site | Listener |
| --- | --- | --- |
| `customer.purchase.completed` | `/api/intake` after Job creation | Schedule repeat-purchase coupon email |
| `pos.payment.completed` | `/api/stripe/pos` after Job creation | Schedule POS coupon email |
| *(future)* `job.status.changed` | Job `afterChange` hook | Notify customer of progress |
| *(future)* `job.completed` | Job status -> delivered/ready_to_ship | Request review |

### Events (Phase 2+ — broadcast)

| Event Name | Trigger Site | Listener |
| --- | --- | --- |
| `campaign.send` | Admin UI | Send to resolved segment via Resend batch |
| `campaign.scheduled` | Cron job | Execute scheduled broadcast |

The dispatcher is the single routing layer — every email trigger flows through it.

### 2D. Segmentation Design (Phase 2)

Broadcast campaigns need to resolve a list of recipient Clients from a filter definition.
The `campaigns.segment` JSON field stores a structured filter that maps to Payload `where`
clauses on the `clients` collection.

**Existing Client fields usable as segment filters** (already in the schema):

| Client Field | Segment Use |
| --- | --- |
| `tags` (array) | "Everyone tagged 'repeat-customer'" |
| `marketing_consent` (checkbox) | Required for ALL broadcasts — never email without consent |
| `portfolio_consent` (checkbox) | "Consented to portfolio" segment |
| `createdAt` | "New customers this month" |

Via **join to Jobs** (requires query expansion):

| Job Field | Segment Use |
| --- | --- |
| `job_type` | "All Studio customers" |
| `status` | "Customers with jobs in progress" |
| `source` | "Website customers only" |
| `stripe_amount_paid_cents` | "High-value customers (> $100)" |

**Segment JSON schema** (stored in `campaigns.segment`):

```ts
interface SegmentDefinition {
  // Direct Client-level filters (ANDed together)
  clientFilters: {
    tags?: { contains: string };         // Client has this tag
    marketing_consent?: { equals: true }; // ALWAYS required for broadcasts
    createdAt?: { greater_than: string }; // ISO date string
  };
  // Optional Job-level filters (requires join — clients with matching jobs)
  jobFilters?: {
    job_type?: 'street' | 'studio';
    status?: string | string[];
    source?: 'website' | 'pos' | 'manual';
    minAmountCents?: number;
  };
}
```

**Segment resolution** (how the broadcast engine builds the recipient list):

1. Start with `payload.find({ collection: "clients", where: clientFilters })`
2. If `jobFilters` present, sub-query Jobs matching those filters, then resolve distinct client IDs
3. Intersect both sets (AND semantics)
4. Deduplicate by email
5. Each resolved Client gets a personalised `EmailEvents` record

This design keeps segmentation explicit and auditable (the segment JSON is stored on the
Campaign record, so you can always see exactly who was targeted).

## 3. Event Dispatcher

New file: `src/lib/events.ts`

A lightweight typed event bus. Designed to be simple now (2-3 listeners) but structured
so that broadcast scheduling and multi-listener fan-out are natural additions.

```ts
// Event payload types — one per event name
type EventPayloads = {
  "customer.purchase.completed": {
    clientId: number;
    email: string;
    firstName: string;
    petName: string;
    jobType: "street" | "studio" | undefined;
    amountCents: number;
    jobId: number;
  };
  "pos.payment.completed": {
    clientId: number;
    email: string;
    amountCents: number;
    jobType: "street" | "studio" | undefined;
    jobId: number;
  };
  // Future broadcast event (Phase 2)
  "campaign.send": {
    campaignId: number;
    segment: SegmentDefinition;
    templateId: string;
    subjectOverride?: string;
  };
};

type Listener<E extends keyof EventPayloads> = (
  payload: EventPayloads[E]
) => Promise<void>;

// Registration
function on<E extends keyof EventPayloads>(
  event: E,
  listener: Listener<E>
): void;

// Dispatch — calls all registered listeners concurrently, swallows errors per-listener
async function emit<E extends keyof EventPayloads>(
  event: E,
  payload: EventPayloads[E]
): Promise<void>;
```

**Key behaviours**:

- Listeners run **concurrently** (Promise.allSettled) — one failing never blocks another
- Each listener's errors are `console.error`'d and do not propagate to the emitter
- No persistence (stateless) — if the process dies between Job creation and listener execution, the EmailEvents record (status: "scheduled") and `email_scheduled_for` date may not be written. This is acceptable: the loss window is milliseconds (a single DB write after job creation), and missing entries are visible as Jobs with `last_email_status = "none"` that should have been scheduled — manually fixable from the admin panel.
- Registration happens at module load time in `src/lib/email-listeners.ts`

**Why this over direct function calls**:

1. Adding a new side effect (Slack notification, analytics ping, CRM tagging) is one `on()` registration — no changes to `/api/intake` or `/api/stripe/pos`.
2. Broadcast scheduling reuses the same `emit("campaign.send", ...)` path with a different listener.
3. Testing: listeners can be swapped for mocks without touching route handlers.

### 3B. Delay Configuration

The email delay is controlled by an environment variable with a sensible default:

```sh
# .env (optional — defaults to 10)
EMAIL_DELAY_DAYS=10
```

In code:

```ts
const EMAIL_DELAY_DAYS = parseInt(process.env.EMAIL_DELAY_DAYS ?? "10", 10);
```

This is read at two points:

1. **Event listener** (scheduling phase) — computes `email_scheduled_for = now + EMAIL_DELAY_DAYS`
2. **Cron endpoint** (sending phase) — queries `email_scheduled_for <= now()` (delay is implicit in the date)

The cron endpoint doesn't actually need the delay value — it just looks for any row whose
scheduled date has arrived. The delay only matters at scheduling time.

## 6. Email Service (Two-Phase: Schedule + Send)

New file: `src/lib/email-service.ts`

### Phase A — Schedule (runs in event listener, immediate)

When a Job is created, the event listener does NOT send email. It only **schedules** it:

1. Receive typed event payload from the dispatcher
2. Compute `email_scheduled_for = new Date(Date.now() + EMAIL_DELAY_DAYS * 86400_000)`
3. Create `EmailEvents` record with status: `scheduled`
4. Update `Jobs.last_email_status = "scheduled"`
5. Update `Jobs.email_scheduled_for`

This is a single fast DB write — the critical window is milliseconds.

```ts
async function handlePurchaseCompleted(
  eventPayload: EventPayloads["customer.purchase.completed"]
): Promise<void> {
  const payload = await getPayload({ config: configPromise });
  const delayDays = parseInt(process.env.EMAIL_DELAY_DAYS ?? "10", 10);
  const scheduledFor = new Date(
    Date.now() + delayDays * 24 * 60 * 60 * 1000
  ).toISOString();

  await payload.create({
    collection: "email-events",
    data: {
      event_name: "customer.purchase.completed",
      channel: "transactional",
      recipient: eventPayload.email,
      template: "repeat-coupon",
      status: "scheduled",
      job: eventPayload.jobId,
      client: eventPayload.clientId,
    },
  });

  await payload.update({
    collection: "jobs",
    id: eventPayload.jobId,
    data: {
      last_email_status: "scheduled",
      email_scheduled_for: scheduledFor,
    },
  });
}
```

### Phase B — Send (runs via cron, deferred)

The actual email send happens in a separate endpoint, driven by Vercel Cron:

```ts
// src/app/api/email/send-scheduled/route.ts
export async function GET() {
  const payload = await getPayload({ config: configPromise });
  const now = new Date().toISOString();

  // Find all EmailEvents scheduled and due
  const pending = await payload.find({
    collection: "email-events",
    where: {
      and: [{ status: { equals: "scheduled" } }],
    },
    limit: 50,  // batch size — Vercel cron has a 10s timeout on hobby, 300s on pro
  });

  // Filter client-side — email_scheduled_for lives on Job, not EmailEvent
  // Alternative: query Jobs with last_email_status=scheduled + email_scheduled_for <= now
  // then resolve the linked EmailEvent. Either approach works.

  for (const event of pending.docs) {
    // Guard: skip if the linked Job's scheduled_for hasn't arrived yet
    if (typeof event.job === "number") {
      const job = await payload.findByID({ collection: "jobs", id: event.job });
      if (!job?.email_scheduled_for || job.email_scheduled_for > now) continue;
    }

    // Render + send
    const result = await sendViaResend({
      to: event.recipient,
      subject: `Your portrait order — confirmed`,
      html: `...`,
      text: `...`,
    });

    // Update EmailEvent
    await payload.update({
      collection: "email-events",
      id: event.id,
      data: result.success
        ? { status: "sent", provider_message_id: result.messageId, sent_at: now }
        : { status: "failed", error_message: result.error },
    });

    // Update Job
    if (typeof event.job === "number") {
      await payload.update({
        collection: "jobs",
        id: event.job,
        data: { last_email_status: result.success ? "sent" : "failed" },
      });
    }
  }

  return Response.json({ processed: pending.docs.length });
}
```

**Alternative query approach** (simpler, recommended): Query Jobs directly instead of EmailEvents:

```ts
const dueJobs = await payload.find({
  collection: "jobs",
  where: {
    and: [
      { last_email_status: { equals: "scheduled" } },
      { email_scheduled_for: { less_than_equal: now } },
    ],
  },
  limit: 50,
});
```

Then for each Job, find its linked EmailEvent and send.

Add to `vercel.json`:


## 7. Error Handling

Principle: **Email failure must never block CRM record creation.**

The event dispatcher swallows all listener errors — `emit()` always resolves successfully
even if every listener throws. Route handlers do not need try/catch around `emit()`.

```ts
// In /api/intake/route.ts — no try/catch needed
await emit("customer.purchase.completed", { ... });
// Job is already created. Email failure is logged by the listener and visible
// in the EmailEvents collection.
```

For Phase 2 broadcasts, the Campaign record tracks `sent_count` and `status` — a
partially-failed broadcast can be inspected per-recipient via the EmailEvents collection.

## 8. Severability & Component Boundaries

The email module is designed to be **severable** — it can be completely removed or disabled
without affecting CRM operations. Each layer has a single, well-defined overlap point with
the rest of the codebase.

| # | Where | What | Severance action |
| --- | --- | --- | --- |

### Disabling Without Removing Code

Set an env var to bypass the entire module:

```sh
EMAIL_ENABLED=false
```

Guarded at the emit sites:

```ts
if (process.env.EMAIL_ENABLED !== "false") {
  await emit("customer.purchase.completed", { ... });
}
```

This is the kill switch. When `false`, no EmailEvents are created, no emails are scheduled,
no Resend calls are made. The CRM operates exactly as it does today.

## 9. Admin Audit Trail

All email activity is fully visible in the Payload admin panel. Nothing is hidden.

### EmailEvents Collection (full history)

Navigate to `Admin > Collections > Email Events`. Every single email — scheduled, sent,
failed, bounced — has a record here. Filterable by:

- `status` — see all failed emails at a glance
- `channel` — transactional vs broadcast
- `event_name` — which trigger produced this email
- `client` — all emails sent to a specific customer
- `job` — all emails linked to a specific job

Each record shows:

| Field | What it tells you |
| --- | --- |
| `recipient` | Who received (or would have received) the email |
| `template` | Which template was used |
| `status` | `scheduled` → `sent` → `delivered` (or `failed` / `bounced`) |
| `provider_message_id` | Resend's internal ID — use this to debug with Resend support |
| `error_message` | Exact error from Resend if the send failed |
| `sent_at` | When Resend accepted the email |
| `delivered_at` | When the recipient's mail server accepted it (Phase 2 webhook) |

### Jobs Collection (at-a-glance)

Each Job shows `last_email_status` and `email_scheduled_for` in the list view.
A Job with `last_email_status = "failed"` has a corresponding `EmailEvent` with
`error_message` explaining why.

### Failure Visibility

If the cron endpoint fails to send a scheduled email:

1. `EmailEvents.status` stays `scheduled`
2. The next cron run picks it up again (idempotent — won't double-send because the
   status is still `scheduled`, and the send phase writes `sent` immediately after
   Resend accepts it)

If the event listener fails to schedule (process crash between Job creation and
`emit()` completing):

1. Job shows `last_email_status = "none"`
2. No EmailEvent record exists
3. Visible as: a paid Job with no email status — manually trigger from admin

### Manual Re-Send (Phase 2)

A custom admin button on the Job detail view that:

1. Looks up the Job's linked EmailEvent
2. Re-renders the template with current Job data
3. Sends via Resend
4. Creates a new EmailEvent record (preserving the old one as history)
5. Updates `last_email_status`

```sh
pnpm payload migrate:create
```

The migration adds:

- `email_events` table (Postgres)
- `last_email_status` column on `jobs` table
- `email_scheduled_for` column on `jobs` table

Run types regeneration after:

```sh
pnpm generate:types
```
