# Risk Analysis: Post-Purchase Coupon Email — Business Failure Modes

**Scope**: `docs/020.1--llm--post-purchase-auto-email-impl.md` and `docs/020.2--llm--post-purchase-auto-email-testing.md`
**Date**: 2026-06-21
**Review basis**: Architecture spec (020.1) + test plan (020.2) + current codebase inspection

---

## Context Summary

The system sends a **repeat-purchase coupon** to customers 10 days after they buy. It uses a two-phase model:

- **Phase A (schedule)**: Event listener writes `EmailEvents` (status=scheduled) and sets `Jobs.email_scheduled_for = now + 10 days`.
- **Phase B (send)**: Vercel Cron daily at 10:00 UTC queries Jobs with `last_email_status = scheduled AND email_scheduled_for <= now()`, renders template, sends via Resend, updates status.

Two templates exist: `repeat-coupon` (website buyers, includes pet name) and `pos-coupon` (POS buyers, no pet name). The email is **not** a receipt — Stripe handles receipts independently.

---

## Risk Matrix

### 1. Malformed Email with Wrong Data

**What happens**: Customer receives an email with a different customer's name, wrong pet name, or literal `{{undefined}}` in the body.

**Root causes identified**:

- **Template rendering falls back on empty strings, not errors**: The spec says "fallback to empty string or 'your pet'" for missing variables (Test Plan Step 8). This means a `{{petName}}` that resolves to empty string produces "A gift for  —" in the subject line. No crash, but a broken-looking email.
- **No type-safety between render() and its callers**: `sendTransactionalEmail()` accepts `data: Record<string, string | number>`. Nothing verifies that the keys match the template's expected variables. A typo in a variable name at the call site silently renders empty.
- **POS jobs have no pet data** — handled by using a separate `pos-coupon` template that doesn't reference `{{petName}}`. But if the template renderer is called with the wrong template ID for the job type, the mismatch produces garbage.
- **The intake form allows empty pet_name** (`pets: [{ name: (formData.get("pet_name") as string) || "" }]` at `src/app/api/intake/route.ts` L166). A job with `pet_name = ""` renders `repeat-coupon` with an empty pet name.

| Category | Rating |
| ---------- | -------- |
| Likelihood | **Medium** — missing data is common (intake form with empty fields, POS jobs, race conditions) |
| Impact | **High** — erodes trust, looks unprofessional, customer may flag as phishing |
| Mitigation | Add required-field guards at render time: if a template variable is empty, either (a) use a hardcoded fallback ("your pet"), (b) skip the send and log a warning, or (c) validate at schedule-time that the Job has all data the template needs. Add unit tests that render each template with deliberately missing fields and assert no `{{}}` or empty awkwardness reaches the output. |

### 2. Duplicate Coupon Emails to Same Customer

**What happens**: A customer buys twice within the 10-day window, or the cron endpoint is called multiple times, and the customer receives two (or more) identical coupon emails.

**Root causes identified**:

- **Per-Job scheduling, not per-customer**: The spec explicitly says "each Job can have multiple email events at different times" (Test Plan Step 4). If a customer buys on day 1 and day 5, two EmailEvents are created and both fire — the customer gets two coupon emails. This is by design, but the business impact is unexamined.
- **Cron idempotency only prevents re-sending the SAME event**: The guard is `last_email_status = "scheduled"` → moves to `"sent"` after Resend accepts. Calling cron twice processes 0 records on the second run. This works correctly. But two separate purchases create two separate scheduled events — both will fire.
- **No "already received a coupon in the last N days" check**: There is no query that says "has this customer received ANY coupon email recently?"

| Category | Rating |
| ---------- | -------- |
| Likelihood | **Medium** — repeat purchases happen in the portrait business; customers may buy a second portrait before the first one ships |
| Impact | **Medium** — annoying to the customer, may trigger spam complaints if they receive two "exclusive" coupon offers, but not catastrophic |
| Mitigation | Add a cooldown check at schedule time: query EmailEvents for this client with template in (`repeat-coupon`, `pos-coupon`) created in the last 30 days. If found, skip scheduling (or update the existing coupon's scheduled date). Alternatively, accept per-Job sending but vary the coupon code/value so it doesn't look like a duplicate mistake. |

### 3. Resend Domain Reputation Tanks

**What happens**: Emails go to spam folders. Customers never see the coupon. No repeat business.

**Root causes identified**:

- **No delivery monitoring in Phase 1**: The spec defers Resend delivery webhooks to Phase 2. In Phase 1, status never advances beyond `sent` (Resend accepted the send). There is **no visibility** into whether an email was delivered, went to spam, or bounced. The operator would only discover the problem when customers complain or repeat business drops.
- **No bounce/complaint handling**: If a customer's email bounces or they mark it as spam, Resend receives that signal on their side, but the CRM never learns about it. The same customer could be sent future emails without the operator knowing the address is bad.
- **SPF/DKIM/DMARC setup is a manual checklist** (Test Plan Step 9): If DNS records are incorrect or expire, emails silently fail or go to spam. No automated DNS health check.
- **Domain warm-up**: If this is a new sending domain or Resend IP, sending volume must be ramped gradually. The cron sends up to 50 per day. This volume is low enough to not trigger spam filters, but if there's a backlog of 500 unsent emails, a single cron run could send them all and look like a burst.

| Category | Rating |
| ---------- | -------- |
| Likelihood | **Low** — Resend is a reputable provider with good deliverability defaults; domain verification is part of setup |
| Impact | **High** — if emails go to spam, the entire feature is wasted; no repeat business generated; domain reputation damage can take weeks to recover |
| Mitigation | Implement Resend delivery webhooks in Phase 1 (not Phase 2) — at minimum track `delivered`, `bounced`, and `complaint` statuses. Add a cron limit soft cap (25 instead of 50 for the first month). Create an admin dashboard widget showing delivery rate (delivered / sent × 100). Set up Resend's built-in webhook alerts for bounce/complaint spikes. Run a DNS health check weekly (SPF/DKIM/DMARC still valid). |

### 4. Customer Who Opted Out of Marketing Receives the Email

**What happens**: A customer who explicitly declined marketing (`marketing_consent = false` on Clients collection) receives a coupon email. They report it as spam or file a complaint.

**Root causes identified**:

- **Transactional vs. marketing distinction is blurry**: The spec says Phase 1 emails are "transactional" and therefore exempt from the `marketing_consent` check (see Test Plan risk table: "Email sent without consent — `marketing_consent` check (not in Phase 1 transactional, but critical for Phase 2 broadcasts)"). Under CAN-SPAM, transactional emails (order confirmations, shipping updates) don't require opt-in. Under GDPR, even transactional emails need a lawful basis — but "performance of a contract" covers order-related communication.
- **A 10-day-delayed repeat-purchase coupon is arguably marketing**: It's not a receipt, not a shipping update, not an account alert. It's a promotional offer designed to drive a second purchase. Regulators could classify it as marketing regardless of how it's labeled internally. The GDPR standard for "legitimate interest" is stricter — if a customer opted out, sending a coupon 10 days later is hard to defend as a contractual necessity.
- **No consent check anywhere in the scheduling or sending path**: Neither Phase A nor Phase B queries `Clients.marketing_consent`. The event listener receives `clientId` (via `EventPayloads["customer.purchase.completed"].clientId`) but only uses it to link the EmailEvent record — it never reads the Client's consent field.
- **The Clients collection has the field** (`src/collections/Clients.ts` L82-88: `marketing_consent: checkbox, defaultValue: false`). It exists and is ready to use. It's just not wired in.

| Category | Rating |
| ---------- | -------- |
| Likelihood | **High** — `marketing_consent` defaults to `false`. Every POS customer and most website customers will have it unchecked. The scheduling logic has no guard. |
| Impact | **High** — GDPR fines (up to 4% of annual revenue), CAN-SPAM penalties ($51,744 per email), Resend account suspension, domain blacklisting, customer trust damage |
| Mitigation | **CRITICAL**: Add a consent check at schedule time (Phase A). Before creating the EmailEvent, fetch the Client and check `marketing_consent`. If `false`, skip the email and log a note on the Job. For maximum safety, consider making the coupon email explicitly opt-in on the intake form itself (a checkbox: "Send me a discount for my next portrait"). Alternatively, reclassify this as a post-purchase follow-up and send it within 48 hours (genuinely transactional timing) rather than 10 days later. Consult a privacy lawyer on classification. |

### 5. Coupon Code Is Expired or Invalid

**What happens**: Customer opens the email, tries to use the coupon code, and it's rejected at Stripe checkout. Customer is frustrated, potentially angry enough to leave a negative review.

**Root causes identified**:

- **No coupon generation system exists**: The `{{couponCode}}` template variable has no backend. There is no `Coupons` collection, no Stripe coupon creation API integration, no code generation logic, and no validation step. The template expects a value that nothing produces.
- **If a static code is used**: A single hardcoded coupon code (e.g., `REPEAT10`) would work but has no per-customer uniqueness, allowing anyone to share it publicly — destroying its value.
- **If Stripe coupons are created dynamically**: There's no `createCoupon()` call anywhere in the architecture. Adding one would require a Stripe API integration that isn't in scope.
- **Coupon expiration**: Even if a coupon is generated, it needs an expiration date that outlives the 10-day delay. A 30-day coupon created at purchase time is valid when sent. A 7-day coupon created at purchase time expires before the email arrives.
- **No usage tracking**: If a coupon is single-use, what happens if the customer clicks the email link but doesn't complete checkout — then tries again? They'd see "coupon already used" through no fault of their own.

| Category | Rating |
| ---------- | -------- |
| Likelihood | **Certain** — the coupon code variable has no implementation. Unless addressed before launch, every email will include an empty, undefined, or placeholder value. |
| Impact | **High** — the entire purpose of the email is to drive a repeat purchase via coupon. If the coupon doesn't work, the email is worse than useless — it actively damages trust ("bait and switch" perception) |
| Mitigation | **BLOCKER**: This must be resolved before ANY emails are sent. Options: (a) Create a Stripe Coupon at job scheduling time with a 60-day expiry and a unique per-customer code (e.g., `REPEAT-{jobId}-{random}`), storing it in a new `Coupons` collection linked to the EmailEvent. (b) Use Stripe Promotion Codes with customer-specific restrictions. (c) Use a generic code with Stripe's `max_redemptions` capped at 1 per customer. Whatever approach, add a pre-send validation in the cron endpoint: verify the coupon is still active in Stripe before sending the email; if expired/invalid, skip the send and log. |

### 6. Resend Outage (3 Days) — Backlog Blast

**What happens**: Resend's API is down for 72 hours. The cron endpoint runs daily, fails to send, and does not update `last_email_status`. On day 4, when Resend recovers, the cron fires and finds all 3 days of accumulated emails — sending them all at once.

**Root causes identified**:

- **Failed sends leave status as `scheduled`**: The cron endpoint's loop structure (spec Section 6, "Phase B") calls Resend, and if it fails, updates EmailEvent to `failed` and Job to `failed`. This is correct per-event handling — each event is marked `failed` on its first cron attempt. It does NOT stay `scheduled`, so on the next cron run it won't be retried.
- **But `failed` events are never retried**: There is no retry logic for `failed` events. If Resend is down for 3 days, the emails that hit the cron on those days are marked `failed` permanently. They only get sent if the operator manually re-queues them. This means the opposite of the question's premise: emails are NOT queued up for a blast — they're permanently lost unless manually recovered.
- **The cron runs at 10:00 UTC daily**: If the cron endpoint itself fails (Vercel function crash, timeout), the scheduled jobs are never processed and never marked failed. On the next run, they're picked up and all sent. But this is a Vercel Cron failure, not a Resend outage.
- **Batch limit is 50**: Even if 200 emails are pending, only 50 are processed per cron run. Subsequent runs on subsequent days pick up the rest. This is a natural throttle.

| Category | Rating |
| ---------- | -------- |
| Likelihood | **Low** — Resend has high uptime (99.9%+ SLA); multi-day outages are rare. The actual failure mode is mark-as-failed-and-never-retry, not blast-on-recovery. |
| Impact | **Medium** — if the cron fails (Vercel issue) rather than Resend, the backlog blast is possible. More likely: emails fail and are never retried, resulting in silent data loss of the coupon opportunity. |
| Mitigation | Add a retry policy for `failed` events: if `error_message` indicates a transient Resend error (5xx, rate limit, timeout), leave status as `scheduled` so the next cron run retries. Only mark `failed` for permanent errors (invalid email, unverified domain, 4xx). Add a maximum retry count (`retry_count` field on EmailEvents, max 3). Add a `daily_send_limit` env var (default 25) to cap per-cron-run volume regardless of backlog. Create an admin alert if any EmailEvent has been in `scheduled` status for more than `EMAIL_DELAY_DAYS + 2` days. |

### 7. Customer Replies to the Email — Who Sees It?

**What happens**: A customer hits "Reply" on the coupon email. The reply goes to `alvar@petportraits.ink` (set as `EMAIL_REPLY_TO` in `.env`). Nobody else sees it.

**Root causes identified**:

- **EMAIL_REPLY_TO is a single address**: The spec sets `EMAIL_REPLY_TO=alvar@petportraits.ink`. This is configured in `.env` and passed to Resend as the Reply-To header. All replies from all coupon emails go to this one inbox.
- **No routing or ticketing integration**: Replies don't create CRM records, don't notify anyone else, and aren't logged in EmailEvents. If Alvar is on vacation or misses the email, the reply is invisible to the rest of the business.
- **Email content doesn't set expectations**: The template (spec Section 5A) mentions `{{supportEmail}}` as a contact address. If the support email matches REPLY_TO, the customer is told to contact the same address they'd reply to — which is fine. But if they're different, replies and support requests go to different places, causing fragmentation.
- **Reply content risk**: A customer might reply with sensitive information (address changes, complaints about the portrait, payment disputes). If this goes to a personal inbox with no CRM logging, there's no audit trail and no way for a team member to follow up.

| Category | Rating |
| ---------- | -------- |
| Likelihood | **High** — customers reply to automated emails regularly, especially ones with a friendly tone and a support contact |
| Impact | **Medium** — missed replies mean missed upsell opportunities or unresolved complaints. A complaint about a portrait that goes unanswered for days because it's in a personal inbox erodes trust. But it won't cause legal/financial damage directly. |
| Mitigation | Set `EMAIL_REPLY_TO` to a shared or monitored address (e.g., `support@petportraits.ink` or a team alias). Add a note in the email body: "Replies to this email are monitored — we typically respond within X hours." Consider a lightweight inbound-email webhook that logs replies to EmailEvents or creates a Client note. In the long term, integrate with a helpdesk. At minimum, document in the team playbook: "Check `alvar@petportraits.ink` daily for customer replies to automated emails." |

## Additional Risks Discovered During Codebase Review

### 8. No Template Exists Yet — Launch Gap

**Risk**: The architecture spec references `src/lib/email-templates/` with `repeat-coupon` and `pos-coupon` as template identifiers, but no template files exist in the codebase. The `sendViaResend()` function will either fail or send empty content if the `templateId` doesn't resolve to real HTML/text. This is a launch-blocker, not a runtime risk — but it means the system cannot go live until templates are built.

| Likelihood | **Certain** (at current state) |
| Impact | **High** |
| Mitigation | Create templates before wiring route handlers (follow spec Step 4 before Step 7). |

### 9. No Email Events Collection — Implementation Gap

**Risk**: The `EmailEvents` collection, `src/lib/events.ts`, `src/lib/resend.ts`, `src/lib/email-service.ts`, and `src/app/api/email/send-scheduled/route.ts` do not exist. The entire email module is unimplemented. None of the risks in this document can be tested or validated yet.

| Likelihood | **N/A** (pre-implementation) |
| Impact | **N/A** |
| Mitigation | Follow the implementation plan (020.1) in order, with the test plan (020.2) validating each step. |

### 10. Brevo and Resend Coexistence

**Risk**: The existing codebase uses Brevo for admin-only notifications (`src/lib/email.ts`). The new module adds Resend for customer-facing emails. Two email providers means two API keys to manage, two billing relationships, two places to check when "email is broken." If Brevo has deliverability issues, admin notifications (new order alerts) stop but customer emails continue — and vice versa. This is a deliberate design choice (spec Section 8 of 020.1) but adds operational complexity.

| Likelihood | **Low** (configuration issue, not runtime bug) |
| Impact | **Low** |
| Mitigation | Document the dual-provider setup in a runbook. Add a health-check endpoint that pings both providers. Consider consolidating to Resend long-term if Brevo admin notifications can be migrated. |

### 11. EMAIL_ENABLED Kill Switch Default-On Risk

**Risk**: The kill switch (`EMAIL_ENABLED=false`) is described as "defaults to true when unset" (spec: `EMAIL_ENABLED !== "false"` is truthy). If an environment variable is accidentally deleted during a deploy or config migration, emails silently turn on. There's no "fail closed" safety — the system defaults to sending.

| Likelihood | **Low** |
| Impact | **Medium** — unwanted emails during maintenance or testing |
| Mitigation | Change the guard to explicitly check for `"true"`: only send if `EMAIL_ENABLED === "true"`. In production, set `EMAIL_ENABLED=true` explicitly. In staging/dev, set `EMAIL_ENABLED=false`. |

### 12. Vercel Cron Timeout Risk

**Risk**: Vercel Cron on the Hobby plan has a 10-second timeout. If the render+send loop processes 50 emails and each Resend API call takes 200ms, that's 10 seconds flat — right at the limit. A single slow Resend response could cause a timeout mid-batch, leaving some emails with status `scheduled` and their Resend call incomplete. On the next cron run, the idempotency guard sees them still as `scheduled` and re-sends — producing duplicates.

**Root cause**: The status update (`sent`) happens AFTER the Resend call succeeds. If the process dies between "Resend accepted" and "DB updated to sent", the email was delivered but the status stays `scheduled`. Next cron run sends it again.

| Likelihood | **Low** (50 emails × 200ms is within limits for Pro plan; Hobby is tight) |
| Impact | **High** — duplicate emails to customers |
| Mitigation | Update EmailEvent status to `sending` BEFORE calling Resend, then to `sent` after. If a crash happens, the cron sees `sending` (not `scheduled`) and skips it. Or query Resend for the message ID before re-sending (requires storing `provider_message_id` at `sending` stage). Reduce batch size to 25 for safety. |

### 13. Customer Data Staleness at Send Time

**Risk**: The email is scheduled at purchase time but sent 10 days later. If the customer's email changes, their name is corrected in the CRM, or they request deletion, the email still goes to the old address with the old data. The EventPayload is captured at emit time and never refreshed.

**Root cause**: The cron endpoint renders the template using data from the Job (via `payload.findByID`), not from the cached event payload. So email address and name WILL be refreshed at send time. However, if the customer was deleted from the CRM in those 10 days, the Job lookup may fail or return incomplete data.

| Likelihood | **Low** |
| Impact | **Medium** — GDPR right-to-erasure violation if a deleted customer still receives email |
| Mitigation | At send time (Phase B), re-verify the client exists, is not deleted, and the email address is still valid. If the client was deleted, cancel the send and mark the EmailEvent as `cancelled` with a note. |

## Highest Priority Actions (Before Launch)

1. **BLOCKER — Coupon code generation** (Risk #5): A coupon email without a working coupon code is worse than no email. Implement Stripe coupon creation at scheduling time.

2. **BLOCKER — Marketing consent check** (Risk #4): Add `marketing_consent` verification at Phase A scheduling. Do not schedule emails for clients with `marketing_consent = false`.

3. **Template variable validation** (Risk #1): Ensure templates degrade gracefully with missing data. Test each template with deliberately malformed input.

4. **Vercel Cron duplicate guard** (Risk #12): Use a three-state status (`scheduled` → `sending` → `sent`) to prevent duplicate sends if the process crashes mid-batch.

5. **Reply-to monitoring** (Risk #7): Confirm `EMAIL_REPLY_TO` address is actively monitored and replies are handled within 24 hours.
