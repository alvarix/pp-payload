# Post-Purchase Coupon Email: Test Plan & Stepwise Validation

Responds to [020.1--llm--post-purchase-auto-email-impl](./020.1--llm--post-purchase-auto-email-impl.md).

This document outlines manual testing tasks, why each matters, and a
step-by-step implementation order where each step is verified before
proceeding to the next. The goal is to never be more than one broken
step away from a working system.

---

## Why Testing Each Step Matters

This module sends automated emails to real customers. The failure modes
that hurt the business are:

| Risk | Business Impact | Prevention |
| --- | --- | --- |
| **Duplicate sends** | Customer receives the same coupon multiple times — looks amateur, may trigger spam complaints | Idempotent cron + status guard |
| **Malformed email** | Missing variables (`{{undefined}}`), broken HTML, wrong customer name — erodes trust | Template testing with real data shapes |
| **Wrong recipient** | Customer A gets Customer B's pet name/coupon — privacy concern, embarrassing | Verify recipient mapping at each step |
| **Email sent without consent** | Marketing email to someone who didn't opt in — GDPR/CAN-SPAM violation | `marketing_consent` check (not in Phase 1 transactional, but critical for Phase 2 broadcasts) |
| **Spam classification** | Emails land in spam — coupon never seen, no repeat business | Resend delivers via verified domain, warm-up, proper SPF/DKIM/DMARC |
| **Silent failure** | Email silently fails, no one knows — opportunity lost, customer thinks you ghosted them | EmailEvents audit trail + `last_email_status` visible in admin |

---

## Implementation & Test Steps

Each step produces a testable artifact. Do NOT proceed to the next step
until the current step's verification passes.

### Step 1: Resend Provider — Send a Single Test Email

**Files**: `src/lib/resend.ts`, `.env`

**What to implement**:

- `pnpm add resend`
- Add `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO` to `.env`
- Create `src/lib/resend.ts` with `sendViaResend({ to, subject, html, text })`
  returning `{ success, messageId?, error? }`

**How to test**:

Create a temporary test script or API route that sends ONE email to yourself:

```ts
// Temporary: src/app/api/email/test/route.ts
import { sendViaResend } from "@/lib/resend";

export async function GET() {
  const result = await sendViaResend({
    to: "alvar@petportraits.ink",       // YOUR email
    subject: "Test email from pp-crm",
    html: "<h1>Test</h1><p>If you see this, Resend is working.</p>",
    text: "Test. If you see this, Resend is working.",
  });
  return Response.json(result);
}
```

Visit `/api/email/test` in the browser. Check email.

**Verification checklist**:

- [ ] Email arrives in inbox (not spam)
- [ ] `success: true` and `messageId: "res_..."` in response
- [ ] Sender is `orders@petportraits.ink` (or whatever EMAIL_FROM is)
- [ ] HTML renders correctly in Gmail / Apple Mail / Outlook
- [ ] Plain text fallback is readable
- [ ] Resend dashboard shows the send at resend.com/overview

**Why this matters**: If Resend isn't configured correctly (wrong API key, domain not
verified, DNS records missing), everything else fails silently. Catch it here.

**Delete the test route after verification.**

### Step 5: Cron Endpoint (Send Phase) — Verify Email Arrives

**Files**: `src/app/api/email/send-scheduled/route.ts`

**What to implement**:

The GET endpoint that:

1. Finds Jobs with `last_email_status = "scheduled"` AND `email_scheduled_for <= now()`
2. For each, finds linked EmailEvent
3. Renders template via `src/lib/email-templates/`
4. Sends via `src/lib/resend.ts`
5. Updates EmailEvent to `sent`/`failed`, Job to `sent`/`failed`

**How to test**:

First, ensure Step 4 created a scheduled EmailEvent with `EMAIL_DELAY_DAYS=0`
(so `email_scheduled_for` is in the past).

Visit `/api/email/send-scheduled` in the browser.

**Verification checklist**:

- [ ] Response shows `{ processed: N }` where N >= 1
- [ ] Email arrives in inbox with correct template content
- [ ] Subject line is correct
- [ ] `{{customerName}}` and `{{petName}}` are resolved (not literal `{{...}}`)
- [ ] Coupon code is present and readable
- [ ] EmailEvents record updated: `status: "sent"`, `provider_message_id: "res_..."`, `sent_at` populated
- [ ] Job updated: `last_email_status: "sent"`
- [ ] Calling `/api/email/send-scheduled` AGAIN processes 0 records (idempotent — already-sent emails are skipped)

**Why this matters**: This is the moment the email leaves your infrastructure. Everything
before this was preparation. Verify the full pipeline: DB -> template -> Resend -> inbox.

**Call the endpoint 3 times in a row** — the second and third calls should process 0
records. If they process > 0, the idempotency guard is broken and you have a duplicate-send bug.

### Step 8: Error Cases — Verify Graceful Degradation

**What to test**:

| Scenario | How to trigger | Expected behaviour |
| --- | --- | --- |
| Resend API key invalid | Temporarily change `RESEND_API_KEY` to `re_badkey` in `.env`, call cron endpoint | EmailEvent status -> `failed`, `error_message` populated, Job `last_email_status` -> `failed`. No crash. |
| Template variable missing | Remove `petName` from the emit payload, call cron endpoint | Template renders without pet name (fallback to empty string or "your pet"). No crash, no `{{undefined}}`. |
| Cron called with no pending emails | Call `/api/email/send-scheduled` when nothing is due | `{ processed: 0 }`. No error. |
| EmailEvents record deleted manually | Delete the EmailEvent for a scheduled Job, call cron | Cron skips the Job (no linked EmailEvent found). Job stays in `scheduled` state — visible in admin as an orphan. |
| `EMAIL_DELAY_DAYS` not set | Remove from `.env`, restart | Defaults to 10. `email_scheduled_for` is 10 days out. |

**Why this matters**: Graceful degradation is the difference between "email failed for one
customer, rest of CRM works fine" and "one bad email took down the intake form."

## Quick Reference: Debugging a Failed Send

1. Open Admin > Email Events
2. Filter by `status = failed`
3. Read `error_message` — this is the exact Resend API error
4. Common errors:
   - `"The from address is not verified"` → Resend domain verification incomplete
   - `"The to address is not valid"` → Customer email is malformed
   - `"Rate limit exceeded"` → Too many sends in a burst (unlikely for transactional)
5. Fix the root cause
6. Manually re-send from admin (Phase 2 feature) or trigger the cron endpoint

## Quick Reference: Emergency Kill Switch

```sh
# In .env (or Vercel env vars):
EMAIL_ENABLED=false

# Redeploy. All email scheduling and sending stops immediately.
# Jobs and intake continue to work normally.
```
