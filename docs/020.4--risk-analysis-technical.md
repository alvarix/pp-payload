# Technical Failure Mode Analysis — Post-Purchase Auto-Email

**Scope**: Implementation plan at [`docs/020.1--llm--post-purchase-auto-email-impl.md`](./020.1--llm--post-purchase-auto-email-impl.md).
**Status**: Plan reviewed; zero implementation code exists in the repo yet. This analysis is based on the plan's stated logic, the existing codebase, and standard Payload/Postgres/Vercel behavior.
**Date**: 2026-06-12

## 1. Idempotency Guard Race Condition — Overlapping Cron Invocations

**Failure scenario**: Two Vercel Cron invocations overlap. Both read the same Job with `last_email_status = "scheduled"` before either writes `"sent"`. Both send the email. Customer receives two identical coupon emails.

**Root cause**: The idempotency check is a **read-before-write** (SELECT then UPDATE) with no locking:

```ts
// Plan pseudocode (Section 6, Phase B)
const dueJobs = await payload.find({
  collection: "jobs",
  where: {
    and: [
      { last_email_status: { equals: "scheduled" } },
      { email_scheduled_for: { less_than_equal: now } },
    ],
  },
  limit: 50,
});
// ... time passes, another cron invocation also finds the same jobs ...
for (const job of dueJobs.docs) {
  await sendViaResend(...);
  await payload.update({ collection: "jobs", id: job.id, data: { last_email_status: "sent" } });
}
```

Postgres default isolation level (Read Committed) does NOT prevent two concurrent SELECTs from seeing the same rows before either UPDATE commits.

**Trigger likelihood**: Low for a daily cron at 10:00 UTC. But HIGH if:

- The cron endpoint is triggered manually via `/api/email/send-scheduled` while the scheduled cron is also running.
- A previous cron run takes longer than expected (e.g., 50 emails × 300ms/email = 15s on Hobby, which exceeds the 10s timeout, causing Vercel to retry).
- Vercel's cron system itself retries after timeout (standard behavior).

**Detection**: Customer reports duplicate coupons. Look for two `EmailEvents` records with `status = "sent"` pointing to the same Job, with `sent_at` timestamps within seconds of each other.

**Severity**: **High**. Duplicate sends to customers are a trust/reputation issue. In the best case, the customer ignores the second; in the worst case, it triggers spam complaints.

**Fix** — use atomic status transition instead of read-then-write:

```ts
// Instead of SELECT then UPDATE, use a single atomic operation:
const claimed = await payload.update({
  collection: "jobs",
  where: {
    and: [
      { last_email_status: { equals: "scheduled" } },
      { email_scheduled_for: { less_than_equal: now } },
    ],
  },
  data: { last_email_status: "sending" }, // intermediate lock state
  limit: 50,
});

// Then send only the jobs that were atomically claimed
for (const job of claimed.docs) { ... }
```

**However**: Payload's Local API `update` with a `where` clause performs a bulk update and returns the updated docs. This is atomic at the SQL level because it translates to a single `UPDATE ... WHERE ... RETURNING *` statement. But the plan's current approach uses `find()` (SELECT) + per-doc `update()` (individual UPDATEs) — this is the non-atomic path.

**Alternative fix**: Use a `sending` intermediate state. The SELECT grabs rows, immediately UPDATEs them to `sending`, then processes only confirmed claims. The `sending` state also acts as a timeout detector — any Job stuck in `sending` for >5 minutes was orphaned by a crash and should be retried.

Another approach: If Payload update with `where` doesn't support atomic claim in the current version, use a raw SQL advisory lock or `SELECT ... FOR UPDATE SKIP LOCKED`.

## 2. Partial Write — EmailEvents/Job Inconsistency (Silent Email Loss)

**Failure scenario**: The schedule phase writes two separate records — an `EmailEvents` doc and a `Jobs` field update — without a transaction. One can succeed while the other fails.

**Scenario 2A** — EmailEvents created, Job update fails:

```
EmailEvents: { status: "scheduled", job: 42 }  ← exists
Jobs #42:    { last_email_status: "none" }      ← never updated
```

The cron queries Jobs by `last_email_status = "scheduled"`, so Job #42 is never found. The EmailEvent sits as an orphan forever. **The email is never sent and no one knows.**

**Scenario 2B** — Job updated, EmailEvents create fails:

```
EmailEvents: (nothing)                           ← create failed
Jobs #42:    { last_email_status: "scheduled" }  ← updated
```

The cron finds Job #42 (status = "scheduled"), tries to find the linked EmailEvent, finds nothing. The plan's error handling says "Cron skips the Job (no linked EmailEvent found). Job stays in scheduled state — visible in admin as an orphan." This case is less severe because the admin can see the orphan Job — but still, the email is never sent automatically.

**Root cause**: No database transaction wrapping the two writes in the event listener (`handlePurchaseCompleted` / `handlePosPaymentCompleted` in the plan's `email-service.ts`). Payload's Postgres adapter supports transactions when you pass `req` between calls, but the event listener doesn't use `req` — it calls `getPayload()` fresh.

**Trigger likelihood**: Low under normal operation, elevated during:

- Network blips between the two DB calls
- Postgres connection pool exhaustion (max 3 connections per the current `payload.config.ts`)
- Vercel function cold start with a slow DB connection

**Detection**: Requires proactive monitoring:

- Query: Jobs with `last_email_status = "none"` that have an EmailEvent pointing to them
- Query: Jobs with `last_email_status = "scheduled"` that have no matching EmailEvent
- Dashboard widget or periodic admin check

**Severity**: **High**. This is a silent failure — no error, no log, no bounce. The customer never receives their coupon and the business loses a repeat-purchase opportunity with no visibility.

**Fix** — three options in order of preference:

1. **DB transaction** (best): Wrap the two writes in a Payload transaction. The event listener should receive or create a `req` object and pass it to both `payload.create` and `payload.update`:

   ```ts
   const payload = await getPayload({ config: configPromise });
   await payload.db.beginTransaction(); // if available, or use req transaction
   ```

2. **Single source of truth** (simpler): Store the scheduled status ONLY on the EmailEvent, not on the Job. The cron queries EmailEvents directly (with a `scheduled_for` field on EmailEvents itself rather than on Job). This eliminates the two-write problem entirely.

3. **Reconciliation cron** (pragmatic): Add a second, less frequent cron that scans for orphans and either fixes them or alerts the admin.

**Note on transaction support in Payload + Postgres**: Payload's Local API supports transactions via `req.transactionID`. The event listener currently uses a fresh `getPayload()` call (no `req`), so there's no transaction context. The fix requires either threading a `req` through from the route handler or using Payload's transaction API directly.

## 3. Cron Timeout Mid-Send — Duplicate on Retry

**Failure scenario**: Vercel Cron has a 10-second timeout on Hobby, 300s on Pro. The cron processes a batch of 50 emails. Resend's API takes ~150-300ms per send. After ~40 emails (roughly 10 seconds), Vercel terminates the function.

The 41st email was sent by Resend (API call returned 200) but the subsequent `payload.update` to mark EmailEvent as `"sent"` never executed. On the next cron run, the Job still shows `last_email_status = "scheduled"`, so the email is sent again.

**Root cause**: The Resend API call and the DB status update are not atomic. The plan's send phase does:

```ts
const result = await sendViaResend(...);  // succeeds
// --- VERCEL KILLS FUNCTION HERE ---
await payload.update({ collection: "email-events", id: event.id, data: ... }); // never runs
```

**Trigger likelihood**: Moderate on Hobby (10s timeout). Low on Pro (300s). Increases with batch size and network latency. Vercel's cron retry behavior after timeout makes this more likely.

**Detection**: Same as #1 — duplicate emails. Look for two EmailEvents with `status = "sent"` for the same Job.

**Severity**: **Medium**. Similar to race condition (#1) but triggered by a different mechanism. The fix for #1 (atomic status transition) also mitigates this.

**Fix**: Use an intermediate `"sending"` status written BEFORE the Resend call:

```ts
// 1. Atomically claim: UPDATE status -> "sending"
await payload.update({ collection: "email-events", id: event.id, data: { status: "sending" } });

// 2. Send
const result = await sendViaResend(...);

// 3. Finalize
await payload.update({ collection: "email-events", id: event.id, data: { status: result.success ? "sent" : "failed" } });
```

If the function crashes during step 2, the next cron run sees `status = "sending"` (not `"scheduled"`), skips it, and a separate "stuck email" detector (or manual admin check) handles orphaned `sending` records. This prevents duplicates at the cost of potentially missing one send (which is better than sending twice).

## 4. `EMAIL_DELAY_DAYS` NaN — Hard Crash in Every Listener

**Failure scenario**: `EMAIL_DELAY_DAYS=abc` (or any non-numeric string) in `.env`.

```ts
// Plan Section 3B
const EMAIL_DELAY_DAYS = parseInt(process.env.EMAIL_DELAY_DAYS ?? "10", 10);
// parseInt("abc", 10) === NaN

const scheduledFor = new Date(
  Date.now() + NaN * 24 * 60 * 60 * 1000
).toISOString();
// new Date(NaN).toISOString() throws RangeError: Invalid time value
```

This crashes the event listener (`handlePurchaseCompleted` / `handlePosPaymentCompleted`). The error is swallowed by the event dispatcher's `Promise.allSettled` (per spec), but the EmailEvents record is never created and the Job is never updated. **Every single purchase silently fails to schedule an email.**

**Root cause**: `parseInt` returns `NaN` for non-numeric strings with no fallback validation. The `??` default only covers the `undefined` case (var not set), not the malformed case.

**Trigger likelihood**: Low in production (env vars are set deliberately). Medium in development (copy-paste errors, missing quotes in `.env`). Consider: Vercel env var UI where someone types `ten` instead of `10`.

**Detection**: No emails are ever scheduled. Admin sees all Jobs with `last_email_status = "none"`. The `RangeError` appears in Vercel logs but is `console.error`'d inside `Promise.allSettled` — it won't trigger alerts unless you're actively watching logs.

**Severity**: **High**. Complete silent failure of the entire email scheduling pipeline. Every single purchase after the misconfiguration produces no email.

**Fix**:

```ts
const raw = process.env.EMAIL_DELAY_DAYS;
const EMAIL_DELAY_DAYS = raw ? parseInt(raw, 10) : 10;

if (Number.isNaN(EMAIL_DELAY_DAYS) || EMAIL_DELAY_DAYS < 0) {
  console.error(`[email] Invalid EMAIL_DELAY_DAYS="${raw}", falling back to 10`);
  EMAIL_DELAY_DAYS = 10; // safe default
}
```

Additional guard: `Math.max(0, EMAIL_DELAY_DAYS)` to coerce negative values to 0 (immediate) rather than dates in the past, or explicitly forbid negative values.

## 5. `EMAIL_DELAY_DAYS` Negative — Immediate Send Flood

**Failure scenario**: `EMAIL_DELAY_DAYS=-5`. `email_scheduled_for` is computed as 5 days in the past. All newly scheduled emails are immediately eligible for the next cron run.

**Root cause**: No lower-bound validation on `EMAIL_DELAY_DAYS`. Negative values produce dates in the past.

**Trigger likelihood**: Low (deliberate config). Could happen accidentally in testing/staging.

**Detection**: Cron picks up "scheduled" emails immediately after purchase instead of after the configured delay.

**Severity**: **Low**. The emails still go out, they're just earlier than intended. For the business use case (repeat-purchase coupon after 10 days), sending early is mildly suboptimal but not catastrophic. However, if the delay is deeply negative (e.g., `-365`), it could interact oddly with date comparisons.

**Fix**: Same validation as #4 — `Math.max(0, EMAIL_DELAY_DAYS)` or reject negative values.

## 6. Template Variable Missing from Event Payload

**Failure scenario**: The `pos-coupon` template references `{{petName}}`, but the POS event payload has no `petName` field (correct — POS sales don't capture pet names). The template renders the literal string `"{{petName}}"` in the customer's email.

```ts
// Plan Section 5B: pos-coupon template
// Variables: customerEmail, couponCode, jobId, supportEmail
// Does NOT include petName or customerName

// But the plan also says templates use {{customerName}}, {{petName}} etc.
// If template references a missing variable, what happens?
```

The plan's template system uses simple string replacement (not Handlebars/Mustache with strict mode). The plan says to "sanitise template variables" but doesn't specify behavior for missing keys.

**Root cause**: The template system (plain HTML/text with `{{var}}` replacement) has no schema validation. Nothing checks that the variables provided match the variables expected by the template.

**Trigger likelihood**: Medium. The plan's POS template already avoids `petName`, but future template additions or copy-paste errors could introduce a mismatch. The plan notes: "Template works without pet name (POS sales have no pet data yet)" but the mechanism for this is unclear (empty string fallback? conditional block?).

**Detection**: Customer receives email with literal `{{variableName}}` text. Looks unprofessional. Customer support may hear about it — or may not, since customers often don't report "your email had weird brackets in it."

**Severity**: **Medium**. Embarrassing but not a system failure. Email is still delivered and readable.

**Fix**:

```ts
function renderTemplate(template: string, data: Record<string, string>): string {
  return template.replace(/\{\{(\w+)\}\}/g, (match, key) => {
    if (key in data) return escapeHtml(data[key]);
    console.warn(`[email] Template variable "${key}" not provided, replacing with empty string`);
    return ""; // empty string instead of literal {{key}}
  });
}
```

Better: use a typed template definition where each template declares its required variables, and the caller must satisfy that contract at compile time:

```ts
interface TemplateDefinition {
  name: string;
  requiredVars: string[];
  render: (data: Record<string, string>) => { subject: string; html: string; text: string };
}
```

## 7. `RESEND_API_KEY` Missing — Fail at Send Time

**Failure scenario**: `RESEND_API_KEY` is not set in `.env` but `EMAIL_ENABLED` is `true` (or unset — defaults to true). The scheduling phase works fine (no Resend call needed). The cron runs, tries to send, and fails with a 401 or API key error.

**Where it fails**: Inside `sendViaResend()` in `src/lib/resend.ts`. The Resend SDK constructor:

```ts
const resend = new Resend(process.env.RESEND_API_KEY);
```

accepts `undefined` without throwing. The actual failure occurs on the first API call: `resend.emails.send(...)` returns an error object with status 401 and message about invalid API key.

**What's the error**: The `sendViaResend()` function returns `{ success: false, error: "..." }`. The cron handler marks the EmailEvent as `"failed"` with the error message. The Job gets `last_email_status = "failed"`.

**Detection**: All EmailEvents show `status: "failed"` with auth errors. Admin sees this in the EmailEvents collection. No customer emails are delivered.

**Severity**: **Low**. The failure is visible (EmailEvents collection shows failures), recoverable (fix the key, manually re-send or wait for Phase 2 manual resend), and doesn't corrupt any data.

**Improvement**: Add a startup/health check that validates `RESEND_API_KEY` is present when `EMAIL_ENABLED` is not `"false"`. Log a clear warning at boot:

```ts
// In src/lib/resend.ts or email-listeners.ts init
if (process.env.EMAIL_ENABLED !== "false" && !process.env.RESEND_API_KEY) {
  console.error("[email] EMAIL_ENABLED is on but RESEND_API_KEY is missing — emails will fail");
}
```

## 8. Job Deleted After Scheduling, Before Cron Runs

**Failure scenario**: A Job is created, the event listener schedules an email (EmailEvents record created, Job updated with `last_email_status = "scheduled"`), and then an admin deletes the Job from the Payload admin panel before the cron runs.

**Two sub-scenarios based on FK constraint behavior**:

**8A — Cascade delete (if EmailEvents.job has `onDelete: "cascade"`)**:
Deleting the Job cascades to delete the EmailEvents record. The email is silently never sent, with absolutely zero trace. No record in EmailEvents, no orphan, nothing.

**8B — No cascade / set null**:
The EmailEvent survives with a dangling `job` reference. The cron (which queries Jobs first) never finds the Job, so never sends. The EmailEvent sits forever with `status = "scheduled"`, pointing to a non-existent Job. Admin sees it as an orphan.

**Root cause**: The plan does not specify `onDelete` behavior for the `EmailEvents.job` relationship field. Payload Postgres generates FK constraints based on the field config. By default, Payload sets cascade behavior depending on whether the relationship is `required`. The spec shows the `job` field as not explicitly `required`, so the default may vary.

**Trigger likelihood**: Low. Admins rarely delete Jobs, and when they do, it's typically for test data or corrections.

**Detection**: For 8A — undetectable. The email simply never happens and there's no record of it. For 8B — visible in EmailEvents if the admin filters by `status = "scheduled"` and notices records with broken job references.

**Severity**: **Medium** for 8A (complete silent loss). **Low** for 8B (visible orphan).

**Fix**: Explicitly set `onDelete` on the relationship:

```ts
// In src/collections/EmailEvents.ts
{
  name: "job",
  type: "relationship",
  relationTo: "jobs",
  hasMany: false,
  required: false,
  index: true,
  onDelete: "set null", // Keep EmailEvent if Job is deleted; allows admin to see what happened
}
```

Or, if Jobs must never be deleted while an EmailEvent references them, add a `beforeDelete` hook on Jobs that checks for pending EmailEvents and warns or blocks the deletion.

## 9. Event Listener Crash Mid-Execution — Partial State

**Failure scenario**: The event listener (`handlePurchaseCompleted`) crashes between the `EmailEvents` create and the `Job` update. This is the runtime manifestation of failure #2.

```ts
// Plan: src/lib/email-service.ts — scheduleRepeatCoupon()
await payload.create({ collection: "email-events", data: { ... } });  // ✅ succeeds
// --- CRASH (OOM, process exit, unhandled rejection) ---
await payload.update({ collection: "jobs", id: ..., data: { ... } }); // ❌ never runs
```

**Root cause**: Two separate DB writes with no transaction. The event dispatcher catches errors (`Promise.allSettled`) but if the Node.js process itself crashes (OOM, SIGKILL from Vercel, uncaught exception in a different part of the app), there's no recovery — the state is permanently partial.

**Trigger likelihood**: Very low for process-level crashes. Higher for transient DB errors (connection drop between the two writes).

**Detection**: Same as #2 — orphan records.

**Severity**: **Low** (same root cause as #2, which is independently rated High; the crash mechanism is just one trigger).

**Fix**: Same as #2 — transaction or single-write approach.

## Additional Observations (Not Part of the 9 Requested Scenarios)

### A. No `vercel.json` Exists

The plan references a `vercel.json` cron configuration, but the file does not exist in the repo (`ls: vercel.json: No such file or directory`). Vercel Cron requires this file. This is a deployment blocker — not a runtime failure, but the send phase won't run at all without it.

### B. Event Listener Registration Path

The plan says: "Registration happens at module load time in `src/lib/email-listeners.ts`" and "Import `src/lib/email-listeners.ts` in a startup path." But it doesn't specify WHERE this import happens. If the import is only in `src/lib/email-service.ts` and neither file is imported by any route handler, the listeners never register at runtime. This is a silent no-op — emails are never scheduled with zero errors. The fix: import in `src/payload.config.ts` (runs at boot) or in each route handler that calls `emit()`.

### C. Postgres Connection Pool Exhaustion

`payload.config.ts` sets `pool: { max: 3 }`. The cron endpoint plus incoming webhook traffic could exhaust this pool. If all 3 connections are busy, the 4th DB operation queues/throws. This could cause the cron to fail mid-batch. Mitigation: use the transaction-mode pooler (port 6543) as recommended in `.env.example`.

### D. Resend API Rate Limiting Not Considered

Resend has rate limits. The plan sends sequentially in a `for` loop, which is slower but safer. If the cron is changed to send concurrently (for performance), it could hit Resend's burst limit and get 429 errors. The plan doesn't mention rate-limit handling.

### E. `email_scheduled_for` Is a String, Compared Against `now`

The plan sets `email_scheduled_for` via `.toISOString()` (a string like `"2026-06-22T10:00:00.000Z"`) and compares it with `new Date().toISOString()`. Payload's `date` field stores this as a proper timestamp in Postgres, and the `less_than_equal` filter handles it correctly — but if `email_scheduled_for` is ever stored as a non-standard format, the comparison silently breaks.
